# Cross-validation

`apbase.cross_validate` is the model-selection engine behind `apbase.Map`.
It compares IDW and ordinary kriging on the same source data using
**leave-one-out cross-validation** (LOO-CV), then lets the pipeline use the
model with the lowest validation error without manual tuning.

## Leave-one-out procedure

For each evaluated source point $x_i$:

1. Temporarily remove $x_i$ (and its value $z_i$) from the source set.
2. Re-estimate a value $\hat{z}_i$ at $x_i$'s location using only the
   remaining $n - 1$ points, with the method under evaluation (IDW or
   kriging).
3. Compare $\hat{z}_i$ to the true, held-out $z_i$.

Repeating this for every evaluated point gives a set of prediction errors
$e_i = z_i - \hat{z}_i$ that reflect how well the method would generalize
to a genuinely new observation at each location -- since each point is
predicted without using its own value.

## Error metrics

Given $m$ evaluated points:

$$
\mathrm{MAE} = \frac{1}{m}\sum_{i=1}^{m} \left| e_i \right|
\qquad\qquad
\mathrm{RMSE} = \sqrt{\frac{1}{m}\sum_{i=1}^{m} e_i^{2}}
$$

$$
R^2 = 1 - \frac{\displaystyle\sum_{i=1}^{m} e_i^{2}}
{\displaystyle\sum_{i=1}^{m} \left(z_i - \bar{z}\right)^{2}}
$$

RMSE penalizes large individual errors more than MAE (useful for
flagging a method that's usually fine but occasionally badly wrong);
$R^2$ expresses how much of the source data's own variance the method
explains, relative to just predicting the mean everywhere.

## Shared variogram, shared neighborhood

Both methods are evaluated against the same fitted variogram/radius and
the same spatial index, so differences in MAE/RMSE/$R^2$ reflect a
genuine difference in interpolation method, not incidental differences in
configuration.

## Bounded runtime

Evaluating every source point exactly is $O(n)$ leave-one-out fits, which
can be expensive for large datasets. `max_points` caps how many points
are evaluated: if the source has more finite points than that, a random
subsample of size `max_points` is drawn instead (seeded by `seed`),
keeping runtime bounded independent of total dataset size.

`apbase.Map` runs this comparison automatically and interpolates with
whichever method scored the lower RMSE. `apbase.create_map` is the
functional shortcut for the same pipeline.

## Cokriging: three methods in one pass

`cross_validate_cokriging` applies the same leave-one-out procedure to
{doc}`collocated, ICM, and LMC cokriging <cokriging>` together. Unlike
`cross_validate`, only the **primary** is held out one point at a time --
each method's coregionalization model is fit once from the full dataset
beforehand and kept fixed throughout, matching how the model is fit once
in practice before repeated interpolation. All three methods still share
one primary spatial index and one radius, so `result.by_method["icm"]`,
`["lmc"]`, and `["collocated"]` remain directly comparable to each other.

## Selecting the best of more than two methods

`select_best_model` compares scores computed on the samples where
*every* candidate method produced a finite prediction. With more than
two methods (e.g. `select_best_model(result.by_method)` from
`cross_validate_cokriging`), the winner and runner-up are fixed from that
point estimate first, then only that pair is paired-bootstrapped for a
significance interval -- a direct extension of the two-method case below,
not a different statistical procedure. Given a plain
`cross_validate(...)` result (IDW vs. kriging), `select_best_model` keeps
its original two-method behavior and return type unchanged.

A paired bootstrap over the common-valid sample estimates whether the
margin between winner and runner-up is likely genuine rather than an
artifact of which points happened to be held out: `n_bootstrap` resamples
of the common-valid indices are drawn once, the winner-vs-runner-up score
difference is recomputed per resample, and `significant=True` when the
resulting confidence interval excludes zero.
