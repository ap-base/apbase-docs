# Translating the documentation

The English pages in `docs/` are the source. Translations live in a folder per
locale that mirrors them file by file:

```
docs/installation.md                 → docs/pt-br/installation.md
docs/user-guide/kriging.md           → docs/pt-br/user-guide/kriging.md
docs/methodology/cokriging.md        → docs/pt-br/methodology/cokriging.md
docs/api/kriging.rst                 → docs/pt-br/api/kriging.md
```

[apbase.io](https://apbase.io) reads these files straight from this repository
and publishes them at `/pt-br/docs/...`, with the same slugs as `/en/docs/...`.
A page that has no translation yet is shown in English, with a notice, until
its file exists. Sphinx ignores `docs/pt-br/` (`exclude_patterns` in
`docs/conf.py`), so `make html` keeps building the English site only.

The API reference is translated too, in a format of its own: see
[The API reference](#the-api-reference). Not translated: `references.bib`
(shared by every language), `img/`, `_static/` and `_templates/`.

## Checking what needs work

```bash
make translations
```

lists pages that are missing in `docs/pt-br/` and translations whose English
page changed after the translation's last commit, with the English commits to
carry over. For the API reference, a new apbase version in
`requirements-docs.txt` counts as a change to every API page. Add `--strict` (`python3 scripts/check-translations.py --strict`)
to fail when anything needs work.

When you update an English page, either update its translation in the same
change or leave it for the report to pick up.

## Rules for every page

- **Same file, same structure.** Keep every heading, list, table, directive and
  tab in the same order as the English page, so both versions can be compared
  side by side.
- **Links keep their targets.** `{doc}` paths stay exactly as in English
  (`` {doc}`../installation` ``); they resolve inside the same language. Give
  links to the API reference an explicit title, because its English pages are
  generated and have no Markdown title to read:
  `` {doc}`referência da API <../api/index>` ``. In a `toctree`, write the entry
  as `Referência da API <api/index>`.
- **Code stays code.** Inside code blocks, translate comments only. Never
  translate function, class, module or parameter names (`Map`, `create_map`,
  `max_neighbors`), string values of the API (`"idw"`, `"kriging"`,
  `"collocated"`, `"icm"`, `"lmc"`, `"light"`) or error names.
- **Keep as written:** math, `{cite}` keys, tab labels (`Python`, `Rust`),
  `:sync:` keys and directive names (`note`, `tab-set`, `tab-item`).
- **No front matter** (`---` at the top of the file): the site renderer does not
  read it.
- **No links to an anchor in another page.** Heading anchors are built from the
  heading text, so they differ between languages. Link to the page instead.
- **Acronyms stay in English** (IDW, RMSE, MAE, IQR, ICM, LMC, MM1, BLUE,
  LOO-CV, NDVI, UTM). The first time each page uses one, expand it in the
  page's language: RMSE (raiz do erro quadrático médio).

## The API reference

The English API pages (`docs/api/*.rst` and `index.md`) are generated by
Sphinx autodoc from the docstrings of the apbase version pinned in
`requirements-docs.txt`. Their translations are Markdown files like every
other page. They write the generated page out by hand with Sphinx's Python
directives, which [apbase.io](https://apbase.io) renders with the same layout
as the English page:

````markdown
# apbase.kriging

::::{py:class} apbase.kriging.Kriging(*, radius=None, max_neighbors=40)

Classes base: `object`

Ajusta um modelo de semivariograma e interpola valores com krigagem ordinária local.

**Parâmetros**

- **radius** (*float | None*) – Raio de busca local. Se for `None`, …
- **max_neighbors** (*int*) – Número máximo de pontos amostrais usados por ponto a estimar.

**Exemplos**

```pycon
>>> from apbase.kriging import Kriging
```

:::{py:property} apbase.kriging.Kriging.radius
:type: float | None

Raio de busca local.

**Retorna**

Raio explícito, ou `None` para derivá-lo do alcance do semivariograma.

:::

::::
````

- **Same objects, same order, same signatures.** One directive per object of
  the English page (`py:function`, `py:class`, `py:method`, `py:property`,
  `py:attribute`, `py:data`), with its full name and the signature copied from
  English. Members go inside their class, whose fence has one more colon.
  Methods add `:classmethod:` or `:staticmethod:`; properties and attributes
  add `:type:`. The full name is the anchor (`#apbase.kriging.Kriging`), the
  same in both languages.
- **Fields and docstring sections** are a bold paragraph of their own followed
  by one block (a list or a paragraph), with the labels in the table
  [Referência da API](#referência-da-api) below.
- **Parameter lines** keep the English shape, `- **name** (*type*) – text`.
  In a type, translate only the words (`or` → `ou`, `default` → `padrão`),
  never the type names.
- **References to objects** use a Python role with the full target, which
  links to the object: `` {class}`Variogram <apbase.variogram.Variogram>` ``.
- **Examples** (`>>>`) stay exactly as in English, in a `pycon` block.

When apbase is bumped in `requirements-docs.txt`, rebuild the English pages,
compare them with the translations and carry the changes over.

## Português (pt-br)

Termos conferidos na literatura brasileira de geoestatística e agricultura de
precisão (Embrapa, ESALQ/USP, SciELO, Acta Scientiarum, RBCS) e na documentação
em PT-BR de QGIS, Google Cloud e Google Earth Engine. Regras gerais:

1. Termo consagrado em português ganha a forma em português: krigagem, efeito
   pepita, patamar, contribuição, alcance, validação cruzada.
2. Termo que a área usa em inglês fica em inglês: outlier, pipeline,
   leave-one-out, lag, raster, worker.
3. Siglas ficam em inglês, porque também são valores da API, com a expansão em
   português na primeira vez em cada página.
